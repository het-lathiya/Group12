## 1. The contract is the source

- **`contracts/openapi.v1.json`** is generated by FastAPI from the Pydantic models in each module's `schemas.py` and committed; it is never edited by hand (`contracts/README.md`). If the specification §6 and the generated document disagree, the generated document is wrong and the change is not merged (§6).
- **`contracts/ai/`** holds the AI JSON Schemas: `gr-1.schema.json` and `gr-2.schema.json` (generation requests), `io-1.schema.json` and `io-2.schema.json` (model output). gr-2 and io-2 add the RAG passages and citations (A1 §6.8).
- **`apps/web/lib/api/schema.d.ts`** holds the web types generated from the contract with openapi-typescript; the web client uses them through openapi-fetch.
- **Check.** `make openapi-check` exports the contract and the web types to a temporary folder and compares them with the committed files. Result in this run (RUN-083, base `f75aa94`): `openapi-check: contracts/ and apps/web/lib/api/schema.d.ts are up to date` (exit 0). So this document points to a current contract.
- **Regenerate.** `make openapi` writes `contracts/` and the web types after any API or schema change. It was **not run** in this run (it writes files; the feature freeze, IMD-201, allows no contract change); `make openapi-check` above shows its output would equal the committed files.

## 3. Conventions

| Topic | Rule (specification §6.1) |
| --- | --- |
| Base path | Resources under `/api/v1`; health at `/health` and `/health/ready` (no version) |
| Format | JSON, UTF-8, snake_case; request models reject unknown fields with 422 (`extra="forbid"`); clients ignore unknown response fields |
| Identifiers | Lower-case hyphenated UUID strings; `day_number` is 1 to 14 |
| Dates and times | Dates `YYYY-MM-DD` (destination calendar); times `HH:MM` local to the destination; timestamps ISO 8601 UTC; durations in whole minutes |
| Money | Two-decimal string next to a `currency` (ISO 4217); ranges `{min, max, currency}`; computed by the backend, never by the browser (IMD-05) |
| Labels | `price_label`, `hours_label`, `cost_label`: `curated`, `estimate`, `unavailable`; `travel_source`: `routing_api`, `fallback_estimate` |
| Pagination | API-08 and API-16 only: `limit` (default 20, 1 to 50) and `offset`; response `items`, `total`, `limit`, `offset` |
| Concurrency | Every itinerary response carries `plan_revision`; every edit, regeneration, restore and named-version request sends it; a mismatch answers 409 `STALE_PLAN` |
| Authentication | `Authorization: Bearer <Supabase access token>` (security scheme `HTTPBearer` in the contract) on every route except API-01 and API-02 |
| Rate limiting | `RATE_LIMIT_PER_MIN` per user on API-16, API-22 and API-25 to API-31: 429 `RATE_LIMITED` with `Retry-After`; daily generation caps answer 429 `AI_QUOTA_REACHED` |
| CORS | Only the origins in `ALLOWED_ORIGINS`; credentials not used |
| Request ID | Every response carries `X-Request-ID`; it appears in the error envelope and in log lines |

## 5. Generation lifecycle

API-22, API-30 and API-31 create a generation and answer 202 with `GenerationOut` (200 when the same request is already active, by `request_hash`). The browser polls API-23 every 2 s, backing off to 5 s, until `status` is `completed` or `failed` (specification §6.4).

| `status` | Meaning |
| --- | --- |
| `queued`, `running`, `validating`, `repairing` | Active |
| `completed` | `outcome` is `model`, `model_repaired` or `fallback_rule_based`; read API-24 |
| `failed` | `outcome` is `failed`; `failure_reason`, `failure_message` and `next_action` say what to do; the previous plan is unchanged |

`GenerationOut` also carries `provider`, `model_id`, `prompt_version`, `repair_attempts`, `deterministic_repairs`, `validation_summary`, `latency_ms` and the A1 retrieval fields `retrieval_mode` (`vector` or `lexical_fallback`), `embedding_model_id` and `retrieval_ms` (A1 §7.1, IMD-116).

Each `Item` in `ItineraryOut` and `EditResultOut` has `sources[]` of type `SourceRef` (A1 §7.1, IMD-116):

| --- | --- | --- |
| `chunk_id` | uuid | `rag_chunks.id` |
| `kind` | `place` or `guide` | `rag_documents.kind` |
| `title` | string | `rag_documents.title` |
| `source_name` | string | `data_sources.name` |
| `licence` | string | `data_sources.licence` |
| `attribution_text` | string or null | `data_sources.attribution_text` |
| `url` | string or null | `rag_documents.url`, else `data_sources.url` |
| `retrieved_on` | date or null | `rag_documents.retrieved_on` |

The list is empty for user-added and rule-based items. The web component `ItemSources` shows it under the AI-written note (FR-139).

## 7. Errors

Every non-2xx response has the envelope `{"error": {"code", "message", "request_id", "details": [{"field", "message"}], "retry_after_s"}}` (`ErrorEnvelope` in the contract). Codes (the contract's `ErrorCode` enum, the same twelve as §6.3):

| HTTP | Code | When |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` | Token missing, malformed, expired or unverifiable |
| 404 | `NOT_FOUND` | Missing, not owned, soft-deleted, inactive, or the route's feature is switched off |
| 409 | `STALE_PLAN` | `plan_revision` is not the stored one |
| 409 | `GENERATION_IN_PROGRESS` | A generation for the trip is active |
| 409 | `CONFLICT` | Other state conflicts (archived trip, itinerary already exists, no itinerary yet, version name taken) |
| 422 | `VALIDATION_ERROR` | Body, path or query fails the schema or a field rule |
| 422 | `INVALID_EDIT` | Structurally impossible edit |
| 429 | `RATE_LIMITED` | Request rate exceeded |
| 429 | `AI_QUOTA_REACHED` | Daily AI generation cap reached |
| 500 | `INTERNAL` | Unexpected fault |
| 501 | `NOT_IMPLEMENTED` | Temporary code for declared but unbuilt handlers; no MVP route answers it (SG-6 row 8) |
| 503 | `SERVICE_UNAVAILABLE` | Database unreachable |

Provider failures are never HTTP errors: they end in the rule-based fallback or in a `failed` generation (§6.3). User-facing wording per code is in [error-catalogue.md](guides/error-catalogue.md).
